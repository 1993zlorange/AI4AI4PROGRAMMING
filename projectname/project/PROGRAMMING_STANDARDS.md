# Web Project Programming Standards

本文件是本模板的强制编程规范。任何实现、测试、脚本、配置、迁移、文档和 release 变更都必须遵守它；`AGENTS.md` 负责说明如何按本规范把内容放入目录。

## 1. 优先级与例外

规则冲突时按以下顺序处理：安全和法律要求、当前明确需求、已批准架构/ADR、本规范、既有局部习惯。确需例外时，缩小到最小范围，在代码附近说明原因，并在 PR 或 ADR 中记录影响、替代方案和撤销条件。禁止用忽略指令关闭整个质量检查来掩盖问题。

关键词：**必须**表示强制要求；**应该**表示默认做法，偏离时需要说明；**可以**表示按场景选择。

## 2. 基线

- 源文件使用 UTF-8 和统一换行符；格式化工具是唯一格式事实来源。
- 锁文件必须提交，依赖只能通过项目声明文件更新。
- 真实日志、构建产物、缓存、上传文件、数据库文件、`.env` 和私钥不得入 Git。
- 代码、配置、迁移、测试和文档必须可由干净 checkout 重现。
- 优先使用项目锁定的 Bun/Node/TypeScript 版本；不得因为个人环境方便而修改工具链版本。
- 生产构建必须可追溯到源码提交、依赖锁文件、配置版本和发布清单。

## 3. 架构与依赖

允许的主方向：

```text
web -> contracts/sdk -> api transport -> application -> domain
                                      \
                                       -> ports -> adapters -> database/external services
worker -------------------------------> application
release/scripts ----------------------> public commands and artifacts only
```

- `domain` 只表达业务规则和值对象，不导入 HTTP、ORM、队列客户端、环境变量或供应商 SDK。
- `application` 编排用例、事务和权限所需的业务策略，通过 `ports` 使用外部能力。
- `api` 负责协议转换、认证、授权、输入校验、错误映射和调用用例，不实现业务规则。
- `adapters` 负责数据库、缓存、消息、对象存储和外部 API 的具体实现。
- `web` 只能通过公共 API/SDK/契约访问后端，不得直连数据库或读取服务器秘密。
- `contracts` 只声明接口和 schema，不放业务副作用。
- `release` 和 `scripts` 可以编排命令，不得复制业务逻辑。
- 禁止使用没有明确所有者的 `utils`、`helpers`、`Manager` 大杂烩模块；新代码应进入实际责任边界。

## 4. TypeScript 与通用代码风格

- 开启严格类型检查；公共导出、边界 DTO、适配器和异步函数必须有清晰类型。
- 禁止 `any`、无解释的类型断言、`@ts-ignore` 和隐式 `undefined`；必要例外必须有范围和原因。
- 优先 `const`、早返回、不可变数据和小而单一职责的函数。
- 不要为了少写几行而过度解构，保留领域对象上下文。
- 不捕获后又吞掉异常；异常必须转换为稳定、可行动的错误或继续抛出。
- 所有网络、文件、数据库、队列和子进程操作都放在边界，通过端口注入，便于测试和超时控制。
- 重试必须有上限、退避、取消和幂等键；不能对非幂等写操作盲目重试。
- 注释解释原因、约束或外部来源，不复述代码表面行为。

## 5. 命名、模块和导出

| 对象                   | 规则                                       | 示例                                    |
| ---------------------- | ------------------------------------------ | --------------------------------------- |
| 文件、目录、变量、函数 | `kebab-case` 目录；代码标识符 `camelCase`  | `request-context.ts`、`loadConfig`      |
| 类型、类、错误         | `PascalCase`                               | `UserSession`、`InvalidConfigError`     |
| 常量                   | `UPPER_SNAKE_CASE` 仅用于真正的常量        | `MAX_PAGE_SIZE`                         |
| 布尔值                 | 使用 `is`、`has`、`can`、`should` 前缀的 `camelCase` | `isReady`                               |
| 测试                   | 描述行为、条件和结果                       | `returnsProblemDetailsWhenTokenExpires` |
| API 字段               | 遵循契约，不因数据库列名而泄露内部实现     | `requestId`                             |

- 一个模块只拥有一个清晰的责任；不要通过 `index` 文件隐藏副作用。
- 公共 API 显式导出；模块加载不能自动注册路由、连接数据库或修改全局状态。
- 文件名和导出名应让读者能判断职责，不使用 `misc`、`common`、`temp` 等模糊命名。
- 功能性代码、脚本、公共配置和测试必须能追溯到 `config/feature-registry.yaml` 的 `feature_id`、`feature_code`、`feature_name`；文件名仍按语言/工具链规范命名，不把功能编号强行塞入导入名。

## 6. API、输入和错误

- 公共 HTTP API 默认使用 `/api/v1`，版本策略必须写在 `packages/contracts` 和 `docs/api/`。
- 所有外部输入都必须在边界校验：类型、长度、格式、枚举、权限和资源归属。
- 错误采用稳定的 `code` 和 Problem Details 风格响应；客户端不得解析堆栈或自然语言。
- 不暴露 SQL、文件绝对路径、访问令牌、内部服务地址或调试堆栈。
- 写操作应定义幂等键、冲突行为、超时和重试语义；分页接口定义上限和排序稳定性。
- 每个新接口必须有成功、参数错误、未认证、无权限、资源不存在、冲突和依赖失败测试（按实际适用范围取舍）。

## 7. 前端规范

- 按 feature 组织页面、数据请求、状态和局部组件；跨 feature 复用才进入 `packages/ui`。
- 页面必须实现加载、空态、错误、权限拒绝、重试和提交中状态。
- 正确处理请求取消、超时、重复提交和过期响应；不要依赖客户端状态作为权限判断。
- 使用语义 HTML、可见焦点、键盘操作、可读错误和适当的 ARIA；关键流程必须有可访问性测试。
- 不把服务器秘密打进前端 bundle；公开配置必须明确列入 allowlist。
- UI 文案、API 错误和日志不得泄露内部路径、凭据或未脱敏个人数据。

## 8. 数据库与迁移

- 数据库访问只能经由 `apps/api` 的 adapter/port 边界。
- 所有 schema 变化必须新增版本化 migration；已共享迁移禁止原地改写。
- 迁移必须记录原因、兼容窗口、锁风险、回填、验证查询和恢复策略。
- 生产使用 expand -> migrate/backfill -> switch -> contract；不能删除旧应用仍读取的字段。
- SQL 值必须参数化；动态表名、排序字段和筛选字段必须 allowlist。
- 种子数据只用于本地/测试，不能把默认账号、生产 token 或真实个人数据放入 `database/seeds/`。
- 备份和恢复脚本必须可审计、可重复并有定期演练记录。

## 9. 配置、日志与安全

- 配置分为默认模板、环境覆盖和秘密；秘密只由运行环境或 Secret Manager 注入。
- 启动时校验配置，错误只指出变量名和修复建议，不打印秘密值。
- 后端和 worker 使用结构化日志，至少包含时间、级别、服务、环境、版本、request ID、trace ID、事件、耗时和错误码。
- 日志必须脱敏授权头、密码、token、个人数据和大文件内容；禁止用日志保存业务事实。
- 健康检查区分 liveness 与 readiness；指标端点必须受网络或认证保护。
- 默认拒绝跨域、文件路径、命令执行和外部 URL；需要放宽时必须 allowlist 并写测试。
- 依赖、容器、机密和权限扫描在 CI 中执行，高危问题必须阻断合并或有审批豁免。

## 10. 测试

- 测试行为和公开契约，不测试实现细节或源代码文本。
- 单元测试保持快速、确定性；适配器优先使用真实实现或最小 fake，不用过度 mock 掩盖集成问题。
- 契约测试防止前后端、SDK 和事件静默不兼容。
- 集成测试覆盖真实数据库/队列适配器、事务、迁移和依赖失败。
- E2E 覆盖关键用户旅程、权限拒绝、重复提交、超时和恢复。
- 性能测试必须写明场景、数据量、基线和阈值；性能测试不能替代正确性测试。
- 新缺陷必须先有能复现问题的回归测试；修复后保留该测试。

## 11. Git、文档和审查

- 一个提交尽量只解决一个可解释的问题；不要把格式化、依赖升级和业务变更混在一起。
- PR 必须说明需求、边界、公共接口/数据/配置变化、测试命令、风险和回滚方式。
- 用户可见行为、API、迁移、配置、日志或部署变化必须同步更新 README、API/运维文档和 CHANGELOG。
- 不提交临时调试代码、真实日志、截图中的秘密、机器绝对路径或未命名 TODO。
- 审查者应优先检查安全、数据损坏、兼容性、并发、错误处理和测试缺口，再检查风格。

## 12. Definition of Done

变更只有在以下条件都满足后才能合并：

- 范围、接口、状态、错误和数据变化与需求/ADR 一致；
- 实现位于正确目录，依赖方向未被破坏；
- 格式、类型、lint、相关测试、契约检查和安全扫描通过；
- 文档、示例、迁移、配置模板和 CHANGELOG 已同步；
- 没有秘密、调试输出、未解释的忽略规则或占位逻辑冒充完成；
- 失败、超时、取消、重试、恢复和回滚路径已按风险验证；
- PR 可由另一位贡献者从干净 checkout 重现。
- 对受本模板治理的工程变更，`F001` 在变更前后通过；项目 Skill 晋升前 `F002` 通过，并保留必要退出码/限制作为内部验证依据；仅实质异常或正式验收需要进入当天同类型记录，不为每次检查另写质量文件。
