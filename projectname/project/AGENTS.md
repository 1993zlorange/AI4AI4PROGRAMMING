# Web Project Template Agent Guide

本文件是编码代理和新贡献者在本模板中的执行规则。**开始编程前必须先阅读并遵守 [PROGRAMMING_STANDARDS.md](PROGRAMMING_STANDARDS.md)**；本文件不能降低编程规范的要求。

## 根级治理协同

开始任何项目相关操作前，必须先回读上级 [AI4PROGRAMMING/AGENTS.md](../../AGENTS.md)，并调用全局 `pr-ps-00-project-supervisor`（主 Skill：`$pr-ps-00-project-supervision`）登记需求、范围、目标文件、权限、风险、验收和日志路径。根级文件负责按风险选择项目经理、架构师、工程师和独立测试能力，`projectname/achieve` 成效归档、人工 Gate 和项目管理记录；本文件只负责 `projectname/project` 的软件工程边界。

工程 Agent 只实现已明确授权的需求/设计或修复目标，已有授权持续有效，普通修复不机械经过所有角色；不得自行扩大产品范围、改变公共 API、数据库 schema、权限、部署方式或验收标准。任何架构冲突先回到 `$pr-ar-01-project-architect` 和项目经理；正式交付时进行必要符合性与独立验收；普通维护按风险做定向验证。失败、阻塞和未执行项必须真实回传根级项目监理。

代码、测试、配置、迁移和工程技术文档留在本目录；正式需求、架构成果、测试/验收报告、用户手册、阶段报告和发布说明写入 `../achieve` 的责任目录。临时数据库、浏览器 profile、截图、trace 和测试输出使用 `output/<类型>/<run-id>/`，不得写入正式数据或项目根。任何新文件先确定唯一用途与责任目录，不另写一套放置报告；简单脚本优先--help及必要注释，使用说明在四份读者文档按需更新，任何文档型 Skill 必须配套中文空白模板。

新增功能、公共接口、数据库迁移、配置能力和用户路径先在 [`config/feature-registry.yaml`](config/feature-registry.yaml) 登记 `feature_id`、`feature_code`、`feature_name`、责任人、实现路径、测试路径和状态，再开始编码；代码文件仍遵循语言命名规范，不为功能编号破坏导入规则。工程变更前后运行 `python scripts/f001_governance_validate.py --project-root ../.. --check` 并保留必要内部证据，不为每次检查另产质量报告。项目 Skill 晋升全局前还必须运行 `python scripts/f002_skill_promotion_audit.py --project-root ../.. --check`；两个工具只读，不能代替人工批准。

## 精简过程记录

从2026-10-30起，record_policy使用process_record_profile=minimal及enabled_daily_types=[requirement, log]。新过程稿只有需求和真实进度日志；授权范围/决定及必要独立意见归相关需求，恢复/重试/检查状态归既有output/run。停止监督、变更、反思、质量、成本、工作契约、交接书独立成稿，不改名“管理报告”继续生成。旧历史和批准原件保留，必要正式设计、验收和发布等实体文档按对象维护；检查与独立评审继续执行，不另造人工内部日报。

## 日记录、内部检查与连续执行

- 同项目、上海记录日和规范类型只允许一个可编辑日文件。类型/固定名称由 `config/feature-registry.yaml` 中record_policy解析，任务、模块、Agent、目录或格式不参与拆分；模板和条目结构见根规则第5.4节。
- 工程测试、代码正确性、格式和恢复检查是内部质量保障，记录在原始output运行证据，不独立生成用户过程结论。用户进度按需求/任务结果和实质异常汇总；科研项目另按其研究要点约束呈现。
- 每条有稳定身份、证据和真实状态；文件已存在就追加，经单写入者/版本检查合并，重复事件不重复写，不用run ID另建当天日志。原始run、配置和固定输入保持各自对象边界。
- 已授权目标内的必要修复、剩余单元、恢复、汇总和复核持续执行。长任务分单元保存断点并有唯一执行者；工具等待结束不等于运行失败，恢复跳过已完成单元。只有触及权限、预算、范围或预设停止条件才暂停相关分支。
- 同一正式文档只有一个当前入口，引用工程证据；已有历史材料原位只读，不为新规批量改名、迁移或补写。

## 科研派生日志的可见范围

普通软件日志绑定requirement_id与实际用户功能变化，不要求研究字段。派生profile为research时，遵循根规则第5.2节group-meeting/1.0：条目同时对应research_point/research_source和guide_questions，以研究问题、actions、result、interpretation、limitations、next_step及真实evidence表达科研推进；performance/analysis须有comparison_conditions和metrics。work_kind只允许literature/method/performance/analysis/writing/research_blocker。

科研日志正文及附录均不得出现代码检查、登记或角色交接流水。没有实际科研变化则不创建科研日志；工程证据仍保存在output，不另建一份人工内部日报。F001按记录日和profile校验，不把软件模板强改为科研项目，不为旧条目补造新合同。

## 1. 项目状态

这是按用户实际需要选择能力的软件工程模板。当前没有产品需求、业务数据库表、可用 API、真实前端页面或生产部署。不要把占位文件描述为已实现功能，也不要在没有批准的需求和 ADR 时补造产品范围。

## 2. 开始任务前

1. 阅读 `PROGRAMMING_STANDARDS.md`，确认命名、依赖、测试、安全和 Definition of Done。
2. 阅读根 `README.md` 和任务相关的 `docs/`、ADR、契约和数据库说明。
3. 把用户请求拆成可验证的行为、接口、数据、错误、配置和运维影响。
4. 检查现有目录和文件，保持已有用户改动，不覆盖无关内容。
5. 如果需求会改变模块边界、数据模型、API 兼容性、权限或部署方式，先补充 ADR 或请求架构确认。

## 3. 文件应该放在哪里

| 任务内容                   | 目录                                       | 规则                                                       |
| -------------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| 页面、路由、feature 交互   | `apps/web/src/`                            | 按 feature 组织；页面通过 API/SDK 调用后端                 |
| Web 静态资源               | `apps/web/public/`                         | 只放可公开发布的资源，不放秘密和运行时上传文件             |
| API 路由和 DTO             | `apps/api/src/api/`                        | 只做协议转换、校验、认证、授权、错误映射和用例调用         |
| 业务规则                   | `apps/api/src/domain/`                     | 不依赖 HTTP、ORM、环境变量和具体供应商                     |
| 用例编排                   | `apps/api/src/application/`                | 管理事务边界和业务流程，通过 ports 使用外部能力            |
| 数据库/队列/外部服务接口   | `apps/api/src/ports/`                      | 定义能力和稳定错误，不绑定具体实现                         |
| 数据库/缓存/外部 API 实现  | `apps/api/src/adapters/`                   | 所有 I/O 在这里，必须有集成测试和超时/重试策略             |
| 日志、指标、追踪、审计     | `apps/api/src/observability/`              | 结构化、脱敏、可关联 request/trace/version                 |
| 异步任务                   | `apps/worker/`                             | 只放独立任务生命周期；任务必须幂等、可重试、可取消和可恢复 |
| OpenAPI、JSON Schema、事件 | `packages/contracts/`                      | 契约是公共接口的单一事实来源                               |
| 共享 UI                    | `packages/ui/`                             | 只放跨应用稳定复用的组件和设计令牌                         |
| 共享工具配置               | `packages/config/`                         | 不放业务逻辑和秘密                                         |
| 客户端 SDK                 | `packages/sdk/`                            | 由契约生成或按契约维护，变更需有兼容性测试                 |
| 数据库结构和变更           | `database/schema/`、`database/migrations/` | 迁移只新增不改写，记录兼容和恢复方案                       |
| 本地/测试种子              | `database/seeds/`                          | 不得放真实数据、默认秘密或生产账号                         |
| 非敏感配置模板             | `config/`                                  | 真实值由环境或 Secret Manager 注入                         |
| 架构/API/开发/运维文档     | `docs/`                                    | 与代码、迁移、配置和发布变化同一 PR 更新                   |
| 跨应用测试                 | `tests/`                                   | 按 contract、integration、e2e、performance、security 分类  |
| 仓库级脚本                 | `scripts/`                                 | 可编排命令，不复制业务逻辑                                 |
| 发布和部署资产             | `release/`                                 | 只放声明式资产、清单、校验、签名、promote 和 rollback      |
| 运行时日志                 | `logs/`                                    | 只保留 `.gitignore` 和说明，禁止提交真实日志               |
| 上传/缓存/临时文件         | `storage/`                                 | 只保留 `.gitignore`，使用显式挂载点或对象存储              |

## 4. 推荐实施顺序

1. 先确认需求、边界、验收标准和是否需要 ADR。
2. 先写或更新 `packages/contracts/` 的接口/schema，再写应用用例和领域规则。
3. 为领域规则、契约和迁移添加测试。
4. 实现数据库、队列和外部服务 adapter，并验证失败、超时、重试和恢复。
5. 接入 API 路由和前端 feature；不要把业务逻辑塞进路由或组件。
6. 更新日志字段、配置模板、API/运维文档和 CHANGELOG。
7. 仅实际发布时更新 release 清单和部署烟测，普通维护不改既有发行快照。
8. 按变更影响运行README中适用的检查；无关全量检查不机械重跑。

## 5. 变更前后检查

开始前回答：

- 这项改动解决哪个需求，成功和失败如何被观察？
- 会不会改变公共 API、数据库 schema、配置、权限、日志或发布行为？
- 哪个目录拥有这项逻辑，依赖方向是否允许？
- 需要哪些单元、契约、集成、E2E、性能或安全测试？

完成前确认：

- 新文件放在责任边界内，没有创建平行的 `frontend/`、`backend/` 或业务副本；
- 没有提交秘密、真实日志、构建产物、机器绝对路径或临时调试代码；
- migration 可在空库和上一版本快照上验证；
- API/SDK/前端/文档/CHANGELOG 已同步；
- 测试不仅覆盖成功路径，还覆盖非法输入、权限、依赖失败、超时、取消和恢复；
- PR 中记录了命令、结果、风险和回滚方式。

## 6. 不确定或发现冲突时

- 不要通过新建模糊目录、复制代码或关闭检查来绕过边界问题。
- 行为、需求、优先级或验收标准不清楚时，先记录问题并请求确认。
- 架构、数据所有权、接口兼容性、安全边界或部署方案冲突时，先写 ADR/设计问题，不要静默重构。
- 发现已有用户改动时，与其兼容；除非用户明确要求，不能回滚或覆盖。

## 7. 代理交付格式

完成任务时说明用户可见结果、需求/ADR关联与必要限制；检查命令和细节留在内部证据，实际异常或影响结果有效性时才说明，不另出常规检查过程报告。不得把“文件已创建”当成“功能已实现”，也不得声称未运行的测试已经通过。


组会要点在可见正文中必须写出具体问题，不能只显示4.4.Q10一类编号。编号保留在机器元数据便于核对，生成器按group-meeting-questions.json展开。面向领导和导师，用完整句说明做了什么、结果说明什么、还有什么不足、接下来做什么；首次解释必要术语，禁止未解释的A/B/C、S0/S1、宏、固定流、待决等简称。保留所有必要数字、条件、负结果和结论边界，不能把改写写成新实验。


## 面向审阅和使用者的四份文档

docs的当前正文只维护四份：README.md、项目技术说明.md、使用指南.md、结果说明与适用范围.md。README负责阅读顺序；技术说明讲项目问题、实际方案和作用；使用指南讲用户需要什么输入、如何操作、得到什么及失败如何处理；结果说明讲实际结果、比较条件、局限和适用范围。面向非实现者，用完整句解释必要术语，不按内部模块、Agent或运行历史组织正文。

机器字段、路径清单、哈希、测试成绩、接口/schema细目、部署参数和过程流水留在配置、代码、--help及既有run，不搬入四份正文或工程附录；正文不使用frontmatter机器身份。必要可复制命令可以保留并说明用途，不把有效操作步骤误当机器清单删除。必要的可操作说明用读者能理解的步骤和明确入口表达，不能删掉影响使用或结果判断的条件；原始证据通过稳定引用定位，不复制第二份事实来源。

旧architecture/api/interfaces/commands/algorithms/adr以及日期API说明不再是默认当前文档骨架。已绑定原件保留原SHA和用途，精确登记为只读来源，不能覆盖旧manifest、改指纹或批量删除。确有独立复杂对象时先说明四文档无法覆盖的理由并获得范围批准，不默认新增对象文档或换名过程报告。

新项目按实际能力选择代码、配置、测试与环境目录，不复制模板维护记录、既有run、历史科研成果或虚假结果；没有实际结果就如实说明尚未取得。四文档采用稳定名称，适用条件用读者可理解的文字说明，机器版本留配置；不同文档按职责维护，不按日期合并。研究日志仍只记录重要真实进展，两类日记录规则保持。新目录在首个具体产物明确后才建，不为填满目录添加能力。

## 新增文件的唯一文件夹归属

新增文件前先按用途确定唯一文件夹和负责对象，再选择文件名；未知类型先说明归属并更新已有策略，未确定前不落盘。不得按本次任务、Agent或执行阶段另造一套目录。仅需求与进度日志按日唯一；实际成果按专题和稳定对象维护，不因同日而合成大杂记。

正式稿、可编辑源与对象专用图归同一成果对象文件夹；跨成果共用结果图在06保留唯一母版。旧版本退出现行导航，但原件与来源保全；版本采用关系未核清时只标未确定，不猜当前稿。写作修改说明、逐句对照、编译检查等过程稿默认不生成，必要原始证据留实施目录已有run；用户明确要求的问答及独立评审内容作为真实附属成果保留。

`achievement_layout` 是既有功能登记中的可选文件夹规则：受管根只允许登记的导航文件，分类下按对象存放，深层子文件由明确用途子树承接；新增未知目录、根散放和过程稿由F001报告。旧件通过相对受管根的精确baseline_paths保留，不用目录通配符豁免新内容；允许目录只在首个实际产物出现时建立，不要求所有分类存在。

软件成果按自身需求与产品、架构设计、测试验收、交付阶段的专题映射，不复制科研八目录。新需求实体归产品需求/使用场景/功能范围，设计实体归系统设计/接口设计/架构决定，正式验收归独立验收/验收材料，交付归用户手册/版本交付/发布说明，各自再按稳定对象建文件夹。
