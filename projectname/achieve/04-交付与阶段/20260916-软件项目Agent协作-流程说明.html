1. 目的、适用范围和结论

本文把当前根级 AGENTS.md、工程级 projectname/project/AGENTS.md 和 reference/ 中的 Agent 使用说明整理成一份可执行的项目流程说明。它回答三个问题：

  1. 一个软件项目从想法到发布要经过哪些角色和关口；
  2. 需求、设计、实现、测试、证据和项目管理记录如何交接；
  3. 哪些事情必须由用户明确决定，不能由 Agent 自动代办。

适用对象是需要前端、API、数据、迁移、测试、运维文档和受控发布的通用软件项目。本文是流程说明，不是需求基线、架构批准、实现完成、测试通过或发布授权。派生项目开始后，应以本项目自己的 AGENTS.md、PRD/SRS、SDD/ADR、测试记录和用户决定为准。

当前模板已经具备治理框架；真实项目仍需通过首个需求完成试点验证。占位目录、规则文件和历史参考不能被描述为已实现产品功能。

2. 总体流程

flowchart TD
    U[用户请求或新项目] --> S[项目监理登记需求、范围、路径、权限和风险]
    S --> PM1[项目经理需求发现与 Requirements Understanding Contract]
    PM1 --> G1{用户确认需求契约?}
    G1 -->|否| PM1
    G1 -->|是| PM2[项目经理形成 PRD/SRS、稳定 ID 和验收标准]
    PM2 --> AR[架构师形成架构/SDD/ADR、接口、数据和迁移设计]
    AR --> G2{用户或项目决策人批准设计?}
    G2 -->|否| PM2
    G2 -->|是| EN[工程师按工作契约实现并自证]
    EN --> PMC[项目经理检查需求/设计符合性]
    PMC -->|不符合| EN
    PMC -->|符合| QA[项目测试在隔离环境独立验收]
    QA -->|FAIL| EN
    QA -->|BLOCKED| B[记录阻塞和所需决定]
    QA -->|PASS| S2[监理核对证据并写日志、变更、质量、成本]
    S2 --> G3{用户明确要求发布?}
    G3 -->|否| C[保留未发布成果和下一步]
    G3 -->|是| R[受控发布、烟测、回滚材料和监理关闭]

核心原则是：先监理登记，再专业执行；先需求确认，再设计和实现；先独立验收，再宣称交付；先用户明确授权，再发布。

5. 新项目启动流程

5.1 建立项目实例

  1. 复制或派生模板，把 projectname 替换为经批准的项目名。
  2. 确认根级 AGENTS.md、工程级 project/AGENTS.md、PROGRAMMING_STANDARDS.md、README 和目录契约可读。
  3. 只在第一份具体记录或产物产生时创建对应目录，不为填满模板批量创建空目录。
  4. 不把本机绝对路径、真实秘密、生产数据或未确认产品事实写入项目规则。

5.2 首次登记

项目监理读取最近根级和目标目录 AGENTS.md，登记：

  • 用户本轮每条要求；
  • 操作范围和非目标；
  • 目标路径和文件归属；
  • 权限、副作用和风险；
  • 验证方式、停止条件和日志位置；
  • 现有工作区状态，避免覆盖他人修改。

没有项目监理记录时，不应进入需求成文、架构设计、编码或测试。

6. 需求阶段

6.1 需求发现

项目经理读取现有需求、设计、日志、测试、用户手册和仓库证据，使用苏格拉底式发现澄清：

  • 用户和目标；
  • 触发条件和输入；
  • 期望输出和状态变化；
  • 失败行为；
  • 范围、非目标和优先级；
  • 权限、数据、成本、兼容性和部署影响；
  • Given/When/Then 验收。

项目经理一次只确认一个会改变范围、验收、架构、成本或权限的关键决定，形成 Requirements Understanding Contract。契约未获用户确认前，不冻结 PRD/SRS，不派发架构或实现。

6.2 PRD/SRS

用户确认契约后，项目经理形成带稳定 ID 的 PRD/SRS：

  • Must / Should / Could / Won't now；
  • 用户路径、输入、输出、错误和持久化行为；
  • 非功能指标和约束；
  • 依赖、风险和失败行为；
  • 每项 Must 的可观察验收方法；
  • 交接给架构师、工程师和测试员的最小包。

需求记录进入 requirements/，历史变化追加，不覆盖。科研成效卡、论文、历史截图或聊天记录只能作为背景证据，不能直接当作已批准软件需求。

7. 架构与设计阶段

需求/SRS 稳定后，项目架构师读取仓库、测试、运行约束和质量属性，输出架构方案、SDD 或 ADR，至少覆盖：

  • 系统边界、信任边界和部署单元；
  • 模块责任与依赖方向；
  • API、文件或事件契约；
  • 数据所有权、schema、索引、事务、迁移、回填和恢复；
  • 错误、权限、配置、观测、安全和回滚；
  • 测试挂钩、实施阶段和验收门；
  • 关键取舍的至少两个候选方案、推荐、代价和反转条件。

接口、数据、约束和测试挂钩必须追溯到 SRS 需求 ID。架构师发现需求不可测或验收不清时退回项目经理，不能通过设计假设补造需求。

设计经用户或项目决策人批准后，才能进入实现。设计未批准前，工程师不得提前编码。

8. 实现阶段

工程师接收已批准需求/设计 ID 和工作契约，先说明：

  • 输入基线和输出产物；
  • 需求/SRS/SDD ID；
  • 文件放置清单；
  • 完成标准和停止条件；
  • 回归影响、测试命令和回滚方式；
  • 需要用户检查的点。

新增功能、公共接口、迁移、配置能力和用户路径先登记 config/feature-registry.yaml 的 feature_id、feature_code、feature_name、责任人、实现路径、测试路径和状态。工程变更前后运行 F001 只读检查。

默认实施顺序：

  1. 契约/schema；
  2. domain；
  3. application；
  4. ports/adapters；
  5. API/页面；
  6. 单元、契约、集成、E2E 测试；
  7. 文档、用户手册和 CHANGELOG；
  8. 发布前质量门。

有 UI 时必须使用真实浏览器检查可见反馈、表单、错误、空态、刷新持久化、键盘、焦点、Console、PageError 和多视口。无 UI 时不虚构浏览器证据。测试数据库、浏览器 profile、截图、trace 和临时产物放在 project/output/<类型>/<run-id>/。

实现中发现需求、接口、数据、权限或部署边界需要变化时，工程师停止当前分支，退回项目经理和架构师，不得静默重构。

9. 对齐检查和独立验收

9.1 项目经理符合性检查

工程师报告完成后，项目经理按 PRD/SRS/SDD 检查：

  • 是否实现全部 Must，未实现项是否明确降级或延期；
  • 用户路径是否可达、可观察、可恢复；
  • API/页面/数据状态是否一致；
  • 文档、配置、迁移和功能登记是否同步；
  • 是否引入未批准范围或架构偏差。

检查不通过时，按偏差 ID 回派工程师；通过只说明实现符合当前基线，不等于独立验收或用户正式验收。

9.2 项目测试独立验收

项目测试从需求、设计和用户手册建立覆盖清单，在隔离数据环境中验证：

  • 页面、按钮、链接、表单和 JavaScript 交互；
  • HTTP 方法、路径、状态码、Content-Type 和正文结构；
  • 成功、无效输入、权限、冲突、重复提交、超时、取消和恢复；
  • 页面显示、API 返回和数据库状态一致性；
  • 刷新后的持久化；
  • Console、PageError、失败请求和响应式布局；
  • 日志、回滚和迁移结果。

测试结论只有三种：

结论 条件
PASS 全部 Must 项有可观察证据，且没有 Critical/High 缺陷
FAIL 存在功能错误、无响应入口、错误返回、状态不一致或 Must 未满足
BLOCKED 已完成诊断，但环境仍阻止有意义测试

FAIL 按缺陷 ID 回派工程师，修复后重新执行项目经理对齐检查和受影响范围复测。不得用旧报告、旧截图、历史计数或“此前通过”覆盖当前状态。

10. 记录、反思和演化

每次原子操作或运行批次结束后，项目监理核对实际路径、命令、结果、未执行项、阻塞、风险、回滚和用户影响，并维护：

记录 回答的问题 位置
需求记录 用户要求什么、边界和验收是什么 requirements/
监督记录 本轮范围、权限、产物、证据和结论是什么 supervision/
项目日志 实际做了什么、验证结果和剩余风险是什么 logs/
反思 目标与事实为何偏离、最小改进是什么 reflections/
变更记录 用户可见和基线变化是什么 changes/
质量记录 执行了哪些门禁、结果和限制是什么 quality/
成本记录 耗时、返工和成本证据是什么 costs/

用户指出问题、确认缺陷、回归、重复失败、质量门阻塞或项目偏离时，触发反思。达到 14 天周期或同类问题 3 次时，进行规则/Skill 演化评估。一般成功只写日志，不自动升级为全局规则。

11. 分层质量门

层级 检查内容 最低证据
L1 路径、命名、功能三元组、目录、文档模板、配置、敏感信息、链接和绝对路径 F001、扫描命令与结果
L2 单元、契约、边界、错误、幂等和兼容 测试结果与失败清单
L3 真实适配器、数据库、迁移、进程、日志和产物 隔离环境运行证据
L4 CLI、HTTP、UI、持久化、恢复和用户路径 可观察状态、响应、截图/trace（如适用）
L5 交付包、文档、许可证、版本、回滚、Skill 晋升和复现 清单、F002、复核和烟测结果

按风险选择层级，不为项目不存在的能力虚构检查。错误阻断；警告必须有处置决定；未执行必须记录原因。

监理关闭条件是：需求逐条有状态，文件归属和命名合规，实现与测试证据真实存在，失败/阻塞/未执行项已记录，项目经理和项目测试结论清楚，日志、变更、质量和成本记录齐全。PASS 仍不代表用户正式验收。

用户提出变更或缺陷
→ 项目监理登记需求/问题、影响和风险
→ 项目经理判断是否改变需求基线、API、数据、权限、部署或验收
→ 需要时更新 Requirements Understanding Contract、PRD/SRS 和稳定 ID
→ 需要时架构师更新 SDD/ADR、schema、接口或迁移方案
→ 用户批准必要基线变化
→ 工程师按新工作契约实现，先列回归影响和文件放置
→ 工程师运行针对性测试和相关质量门
→ 项目经理重新检查需求/设计符合性
→ 项目测试复测受影响功能和相邻回归范围
→ 项目监理记录结果、变更、成本和必要反思

已确认、已实现或已在用户手册/验收证据中展示的功能属于兼容性基线。除非用户明确批准替代或废弃，新功能不得使旧入口悄然消失。每个发现的回归都应有最小自动化资格测试，并说明失败于修复前、通过于修复后的证据。

13. 受控发布流程

默认不发布。只有用户明确命令发布后，才能执行：

  1. 项目监理登记版本范围、授权和排除项；

  3. 工程师准备经批准的源代码、锁文件、迁移/配置模板、必要文档和发布资产；
  4. 项目测试执行发布烟测和关键用户路径验证；
  5. 项目监理复核清单、许可证、秘密排除、证据和回滚材料；

全局 Agent：pr-en-00-engineer

配置：~/.codex/agents\pr-en-00-engineer.toml 主责：已确认软件范围的全栈实现、开发验证、布局治理与用户手册同步

定位

全局 pr-en-00-engineer Agent 是全栈工程师。它不负责决定产品要做什么，而是基于用户已经确认的需求理解契约、SRS 和设计方案，把一个功能从高质量交互前端实现到规范后端和端到端验证。项目内 .codex/agents/pr-en-00-engineer.toml 是当前项目维护副本；角色的运行真源为全局配置。

它固定使用 $pr-en-01-fullstack-design-engineer、$pr-en-02-senior-engineer、$scienceresearch-repository-layout、$playwright 和需要时的 $scienceresearch-user-manual。需求不清退回 pr-pm-00-project-manager；模块边界、数据契约或已批准接口需要改变时，先退回项目经理，并使用 $pr-ar-01-project-architect 完成架构评审后再实施。

工作顺序

  1. 检查用户已确认的需求理解契约、需求/设计/架构基线和范围 ID；有产品歧义时退回 pr-pm-00-project-manager，有架构冲突时也退回 pr-pm-00-project-manager，并用 $pr-ar-01-project-architect 完成架构评审，评审通过后再恢复实现。
  2. 调用 $scienceresearch-repository-layout，阅读 ADR-008、根目录和目标目录，为所有新增、移动、生成或归档文件先写 Placement Plan，明确归属、生命周期、最终路径、引用和清理规则。
  3. 阅读现有原型、页面、设计 Token、路由、接口、测试、用户手册以及离线和无 CDN 约束。
  4. 联网寻找 3～5 个用户或工作流相似的高采用产品/网站，记录 URL、核查日期、热度证据、可借鉴模式和不能复制的边界。
  5. 给出 Design Read：页面唯一任务、用户、视觉语言、信息密度、交互模型、Token、标志性元素和响应式风险。
  6. 先定义最小 UI 到 API/状态合同，再完成可交互前端垂直切片。
  7. 使用真实浏览器检查按钮、表单、错误、空态、冲突、成功反馈、刷新持久化、键盘、焦点、Console、PageError 和 1440/900/390 三视口；测试数据库、浏览器 profile、截图和 trace 必须写入 output/ 下带 run-id 的隔离目录，不得写入正式 data/ 或项目根目录。
  8. 前端交互合同稳定后，按 SDD、$pr-en-02-senior-engineer 和 E:/zl/07-Tools/编程规范.md 实现后端。
  9. 替换开发期临时数据，运行单元、契约、集成、架构和端到端测试，执行目录检查与旧路径引用检查，清理或归档临时产物，写工程日志并交给独立 pr-qa-00-project-test Agent 验收。

文件落盘纪律

工程师不得因为当前工作目录方便、工具默认输出或“先临时放一下”而新建根级目录。产品代码放入 src/scienceresearch/ 的既有架构边界，测试源码/固定 fixture 放入 tests/，正式业务数据只放 data/，测试和浏览器运行产物放入 output/.../<run-id>/，维护型文档放入 doc/，源创意/原型放入 idea/，Agent/Skill 放入 .codex/，用户导出和正式备份分别放入 exports/、backups/。没有现有归属的稳定文件必须先做架构决策，不得自行发明目录。

每次交付前运行：

python .codex/skills/scienceresearch-repository-layout/scripts/check_repository_layout.py .

随后用 rg 检查移动/改名后的旧路径引用，并在交付中给出 Placement Audit。doc/、idea/、data/、log/、output/pr-qa-00-project-test/、output/pm-chain-*、output/playwright/ 均有当前运行或证据引用，不能当作普通整理直接移动。

前端要求

前端必须具有明确的信息层级、原创视觉方向、统一 Token、真实内容形态、完整交互状态、可访问性和响应式布局。不得只做静态截图，不得出现无响应按钮，不得依赖 HTTP 200 代替可见结果验证，不得机械采用紫色渐变、玻璃面板、同质卡片网格和无意义动效。项目现有 idea/科研工作分解与每周组会汇报模板_20260828.html 和已批准设计方向优先于流行趋势。

后端要求

后端保持 domain/application/adapters/interfaces 责任边界，GET 无副作用，输入显式验证，错误码和 HTTP 状态稳定，路径和 subprocess 受控，事务、版本冲突、幂等、恢复和原子文件写入明确。页面、API 和数据库刷新后必须一致。

调用示例

何时不应调用

  • 研究问题、论文结论或 SR 成效卡本身尚未被人确认要转为产品功能时，先由科研项目负责人给出证据与建议，再由 pr-pm-00-project-manager 做需求澄清。
  • 仅需要架构、SDD、接口、数据库或迁移方案而不需要代码时，调用 $pr-ar-01-project-architect，不启动工程师实现。
  • 仅需要独立验收或复现缺陷时，调用 pr-qa-00-project-test；工程师不能代表独立测试给出 PASS。

全局 Agent：pr-qa-00-project-test

配置：~/.codex/agents\pr-qa-00-project-test.toml 主责：独立、只读地验证已实现的软件功能

1. 已配置内容

项目测试能力由三部分组成：

  • ~/.codex/agents\pr-qa-00-project-test.toml：全局独立测试 Agent 的角色、边界和验收规则；项目内 .codex/agents/pr-qa-00-project-test.toml 为维护副本；
  • .codex/skills/scienceresearch-functional-qa/：科研工作台专用的功能覆盖模型、按钮无响应判定规则和报告格式；
  • 用户级 $playwright Skill：OpenAI curated 浏览器自动化 Skill，用于真实页面点击、表单填写、截图、trace、网络和控制台检查。

pr-qa-00-project-test 是只读验收角色。它可以启动隔离的本地服务、创建临时测试数据和保存测试证据，但不会修改产品代码、正式文档或正常 data/ 目录，也不会把失败项自动改成通过。

它固定使用 $scienceresearch-functional-qa 建立覆盖模型，并在可用时使用 $playwright 做真实浏览器交互。它的输入应是已确认的 Must 范围、SRS/SDD、用户手册和待测实现；科研成效卡、论文或仿真图可作为产品需求的背景证据，但不能替代可测试的软件验收条件。

2. 启用方式

Agent 和新安装的 Skill 在新的 Codex 会话中加载。关闭并重新打开当前项目会话，工作目录保持：

<项目根>/scienceresearch

然后使用以下提示：

调用 pr-qa-00-project-test agent，使用 $scienceresearch-functional-qa 对 scienceresearch 执行完整功能测试。逐项测试所有页面、链接、按钮、表单、JavaScript 交互和 API，重点检查点了没反应、返回状态或正文不正确、页面显示与服务端状态不一致、控制台错误、窄屏溢出和键盘不可用。使用临时数据目录，不修改正常 data；把报告、截图和 trace 保存到 output/pr-qa-00-project-test，并给出 PASS/FAIL/BLOCKED 结论和可复现缺陷清单。

也可以执行有针对性的测试：

调用 pr-qa-00-project-test agent，只复测周计划、Evidence、完成门、Recommendation 和报告导出，核对每个按钮的可见结果、HTTP 返回和数据库状态。

调用 pr-qa-00-project-test agent，检查主工作台所有按钮是否有响应，并在 1440、900、390 三种宽度执行键盘和布局测试。

3. Agent 的检查方法

Agent 首先从需求文档、设计方案、项目架构、用户手册、web.py、core.py 和现有测试建立覆盖清单，而不是只根据页面上当前存在的元素判断是否正确。

对每个按钮、链接或表单，Agent 至少检查：

  1. 操作前后的 URL 和页面状态；
  2. 是否产生预期的可见反馈；
  3. 请求方法、路径、HTTP 状态、Content-Type 和正文结构；
  4. 浏览器 console、page error 和失败请求；
  5. 页面刷新后的持久化状态；
  6. API、页面显示和数据库状态是否一致；
  7. 缺少前置条件、错误输入、重复提交和过期版本是否被正确拒绝。

如果点击后既没有跳转、可见反馈、请求、状态变化，也没有可访问的解释，会标记为 NO_RESPONSE。如果发生了动作，但状态码、正文、重定向、页面结果或持久状态错误，会标记为 WRONG_RESPONSE 或 STATE_MISMATCH。

4. 测试证据和结论

每次运行使用：

output/pr-qa-00-project-test/<run-id>/

保存测试报告、覆盖矩阵、截图、trace、响应证据和测试命令输出。最终结论只有三种：

  • PASS：全部 Must 项有可观察证据，且没有 Critical/High 缺陷；
  • FAIL：存在功能错误、无响应按钮、错误返回或未满足 Must 的项目；
  • BLOCKED：经过诊断后，运行环境仍然阻止有意义的测试。

测试报告不会只列失败项，还会列出每个已测试功能的预期、实际结果和证据位置。

5. 修复与复测流程

推荐流程为：

pr-qa-00-project-test 独立测试
  → 工程师 Agent 按缺陷 ID 修复
  → pr-qa-00-project-test 只复测受影响功能和相邻回归范围
  → pr-pm-00-project-manager 做需求/设计对齐与交付状态判断

测试 Agent 本身不实施修复，避免同一个角色既修改代码又证明自己的修改正确。

6. 与科研流程的边界

pr-qa-00-project-test 不验证科学结论、实验可重复性或论文 claim。这些由 sr-experimenter、sr-critical-reviewer 与 sr-principal-investigator 按 SR 工作流处理。只有科研项目负责人和人类决策者确认某项科研成果需要转化为科研工作台功能，并经 pr-pm-00-project-manager 形成可验收的软件范围后，项目测试才进入该功能的交付链。
