项目手册 · 2026-09-16

从一个想法，到一件可信交付

这本手册把当前软件项目流程改写成一条能照着走的路径。你可以把它理解成“盖房子”：先问清业主想住什么，再画图，再施工，再由不施工的人验收；没有业主点头，不能交房。

适合读者新成员 · 项目决策人 · Agent 协作者
当前基线2026-09-15 流程说明
建议时长入门 15 分钟；全览 45 分钟
读完能懂谁先做、谁批准、谁验收、何时能发布

1. 它解决什么问题

AI 参与开发后，最容易出现的不是“完全不会做”，而是下面这些混乱：

想法散

聊天里有很多要求，但没有范围、失败行为和验收标准。

责任散

同一个角色既定需求、又写代码、又说自己验收通过。

证据散

页面能打开就说完成，但不知道数据、恢复和失败路径是否正确。

改动乱

新功能上线了，旧功能悄悄消失。

发布急

没经用户明确授权，就打包、部署或上传。

记录断

做了什么、验证过什么、还有什么风险，之后就找不到证据。

一句话记忆：AI4PROGRAMMING 不是“让 AI 随便写代码”，而是把开发拆成可检查的小闭环：先登记，再确认，再设计，再实现，再独立验收，再授权发布。

2. 快速开始：新项目第一次启动

假设你只有一个模糊想法，例如“我想做一个更好用的教学后台”。不要直接让 AI 写代码，按这张表走：

步骤你要做什么预期看到什么常见错误
1. 项目监理登记说明目标、输入、目录、权限、风险和验收方式。需求记录和监督记录。只说“帮我做个系统”，没有边界。
2. 需求澄清项目经理把模糊想法整理成需求理解契约。用户、触发、输入、输出、失败行为和验收。把聊天记录直接当成需求。
3. 用户确认由你确认范围和优先级。Requirements Understanding Contract 被确认。AI 自己推断成“用户已经同意”。
4. 设计批准架构师给出模块、接口、数据和迁移方案。SDD/ADR 和实施顺序。还没批准设计就开始改架构。
5. 工程实现工程师按契约实现并自证。代码、测试、文档和隔离证据。只测 happy path。
6. 独立验收项目测试用隔离数据检查用户路径。PASS / FAIL / BLOCKED 和证据。用开发者自测代替独立验收。
7. 授权发布用户明确同意后才发布。发布包、烟测和回滚方案。“看起来好了”就自动上线。
新手提示：不确定时先问三个问题——这个功能的输入是什么？失败时应该怎样？什么证据能证明它完成？

3. 10 分钟核心模型

当前项目可以用“三个门槛 + 六个角色”理解。

3.1 三个最重要的门槛

Gate 1用户确认需求需求契约没确认，不冻结 PRD/SRS，不派发设计和实现。
Gate 2设计批准接口、数据、迁移和回滚方案批准后，工程师才能实现。
Gate 3独立验收 + 用户授权测试通过只说明可交付候选；发布仍需用户明确授权。

3.2 六个角色怎么分工

用户 / 项目决策人

像业主。确认要什么，批准关键取舍，决定是否发布。

项目监理

像登记台和安全员。登记范围、路径、权限、风险、记录和关闭状态。

项目经理

像需求翻译官。把想法变成 PRD/SRS、验收标准、计划和状态。

项目架构师

像建筑设计师。定模块边界、接口、数据、迁移、回滚和测试挂钩。

全栈工程师

像施工队。按批准设计实现，写测试，保存证据，不做范围外的事。

项目测试

像独立验房师。用隔离数据检查页面、API、数据和失败路径。

关键边界：写代码的人不能替独立测试下结论；测试通过也不能代替用户决定是否发布。

4. 全流程：从想法到交付

下面是当前流程的主干。每一格都可以追溯到 20260915 流程说明。

1
用户提出请求说清目标、输入、限制和期望结果。入口
2
项目监理登记登记需求、路径、权限、风险、停止条件和日志位置。先登记，后执行
3
需求发现项目经理形成 Requirements Understanding Contract。区分事实 / 推断 / 未知
4
用户确认需求确认前不冻结 PRD/SRS，不派发架构和实现。人工 Gate
5
形成 PRD/SRS写清 Must / Should / Could / Won’t now、失败行为和验收。
6
架构 / SDD / ADR定义边界、接口、数据、迁移、回滚和测试挂钩。
7
设计批准关键取舍由用户或项目决策人批准。人工 Gate
8
工程实现契约/schema → domain → application → adapters → API/UI。
9
项目经理符合性检查核对实现是否符合需求、设计和用户路径。
10
项目测试独立验收隔离数据下检查功能、API、状态、错误、恢复和浏览器。PASS / FAIL / BLOCKED
11
监理闭环记录日志、质量、变更、成本、证据和残余风险。
12
用户明确授权后发布形成版本清单、烟测、回滚方案和发布说明。人工 Gate
回派规则：项目经理检查不符合，回工程师；测试 FAIL，回工程师；BLOCKED 要记录原因和所需决定，不能假装通过。

5. 五个关键关口

关口谁能通过不能怎么替代通过后才能做什么
需求确认用户确认需求理解契约。不能靠 AI 推断或聊天语气。冻结 PRD/SRS，派发架构和实现。
设计批准用户或项目决策人批准 SDD/ADR。不能靠“代码能跑”补设计。工程师按 SDD 实现。
符合性检查项目经理按需求/设计核对。不能靠代码存在或单测通过。交给项目测试独立验收。
独立验收项目测试在隔离环境验收。不能靠开发者自测或旧截图。形成可交付候选。
发布授权用户明确授权。不能靠测试 PASS 自动上线。打包、烟测、发布和记录回滚。

6. 角色怎么做

6.1 项目监理

一句话：先把事实登记下来，再让专业角色干活。

  • 登记需求、范围、路径、权限、风险和验收。
  • 检查文件命名、目录归属和证据。
  • 维护日志、质量、变更、成本和反思。
  • 不批准产品需求，不代替架构、实现、测试或用户验收。

6.2 项目经理

一句话：把“我想要个东西”变成“能验收的需求”。

  • 澄清目标、输入、输出、失败行为和优先级。
  • 维护 PRD/SRS、风险、计划和交接包。
  • 检查实现是否符合需求与设计。
  • 不写代码，也不替代独立测试。

6.3 项目架构师

一句话：先决定房子的结构和水电，再让施工队开工。

  • 定义模块边界、依赖方向、API、数据和事件。
  • 设计数据库、迁移、回填、恢复和回滚。
  • 给出测试挂钩、实施阶段和验收门。
  • 不改写需求，不擅自实现代码。

6.4 全栈工程师

一句话：按批准图纸施工，并留下可复现证据。

  • 先定契约/schema，再做 domain/application/adapters/API/UI。
  • 写单元、契约、集成、E2E 和必要浏览器验证。
  • 更新文档、配置和迁移。
  • 需求或架构不清时停止，不自行扩范围。

6.5 项目测试

一句话：用独立证据判断“用户路径真的能用吗”。

  • 隔离数据下测试 UI、API、持久化、权限、错误和恢复。
  • 检查刷新后状态、Console、PageError 和响应式。
  • 结论只有 PASS / FAIL / BLOCKED。
  • 只读验收，不修改产品代码。

6.6 用户 / 项目决策人

一句话：确认方向、批准取舍、决定发布。

  • 确认需求理解契约和关键设计取舍。
  • 授权高风险动作和发布。
  • 审阅最终结果。
  • 不需要替 Agent 伪造执行证据。
角色协作逻辑图：需求进入 → 项目经理澄清 → 架构师设计 → 工程师实现 → 项目经理检查 → 项目测试复验 → 结论闭环。FAIL 回工程师；BLOCKED 记录决定；PASS 交监理关闭。

8. 质量怎么判

不要只问“能不能跑”，要按风险分层检查。

L1 静态

路径、命名、目录、配置、敏感信息和链接。

L2 单元 / 契约

正常、边界、非法输入、幂等和兼容。

L3 集成

真实数据库、进程、迁移、日志和产物。

L4 用户路径

UI、API、持久化、权限、失败和恢复。

L5 交付

版本、文档、许可证、回滚和复现。

验收结论：PASS 表示全部 Must 有证据且没有 Critical/High 缺陷；FAIL 表示功能错误或 Must 未满足；BLOCKED 表示环境阻断了有意义的测试。

9. 变更和故障怎么办

1
登记问题或变更监理先记录影响、风险和验收方式。
2
判断基线影响是否改变需求、API、数据、权限、部署或验收。
3
更新需求 / 设计必要时更新契约、SRS、SDD/ADR 和迁移。
4
用户批准关键变化改变范围、成本、权限或验收时必须确认。
5
实现与回归工程师列回归清单，补最小资格测试。
6
重新对齐与复测项目经理检查，测试复测受影响范围。
7
闭环记录缺陷、修复、证据、残余风险和经验。
防假完成：旧功能不能因为新功能上线而悄悄消失。回归要有自动化资格测试，并说明“修复前失败、修复后通过”。

10. 发布规则

默认不发布。发布、部署、上传、重启服务或写外部系统，都需要用户明确授权。
阶段做什么不能做什么
授权登记监理记录版本范围、授权和排除项。不能把聊天里的暗示当成发布命令。
发布准备项目经理形成清单、说明、风险和回滚。不能把真实数据、秘密或内部记录塞进包里。
资产准备源代码、锁文件、迁移/配置模板和必要文档。不能缺少回滚方案。
发布烟测测试关键用户路径和回滚路径。不能用旧报告替代本轮烟测。
交付归档结果写入 release 和阶段目录。不能自动部署或上传。

11. 常见误区

“代码存在 = 完成”

错。还要看用户路径、错误、持久化和证据。

“单测过了 = 验收”

错。单测不能替代独立功能验收。

“HTTP 200 = 正确”

错。要检查状态、正文、页面状态和数据库结果。

“AI 说完成 = 完成”

错。要看证据、命令、失败项和未执行项。

“测试通过 = 可以发布”

错。发布还需要用户明确授权。

“旧功能还在底层 = 没丢”

错。用户可达入口消失，也算回归。

12. 一周演练

时间练习目标
周一选一个小需求，走监理登记和需求发现。会写范围、失败行为和验收。
周二形成最小 PRD/SRS。每个 Must 都能验证。
周三做一次小架构评审。明确模块、接口、数据和回滚。
周四实现最小垂直切片。契约、领域、适配器、API/UI 分层清楚。
周五做符合性检查和独立验收。会用 PASS/FAIL/BLOCKED。
周末复盘日志、证据和风险。知道下一步和缺口。

13. 收尾清单

  • 需求逐条有状态，范围外事项没有被静默实现。
  • 文件有责任目录和日期化命名，无机器绝对路径和敏感信息。
  • 实现和测试证据真实存在，失败、阻塞和未执行项已记录。
  • 用户可见路径、错误、权限、持久化和恢复已验证。
  • 文档、配置、迁移和功能登记已同步。
  • 项目经理符合性检查和独立测试结论清楚。
  • 日志、质量、变更、成本记录齐全。
  • PASS 不等于正式验收；发布仍需用户明确授权。
最快判断法：如果你不能回答“谁确认、谁批准、谁验收、谁授权发布、证据在哪”，就还没完成。
