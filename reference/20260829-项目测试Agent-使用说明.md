# 项目测试 Agent 使用说明

> 更新：2026-09-10
>
> 全局 Agent：`pr-qa-00-project-test`
>
> 配置：`C:\Users\PC\.codex\agents\pr-qa-00-project-test.toml`
> 主责：独立、只读地验证已实现的软件功能

## 1. 已配置内容

项目测试能力由三部分组成：

- `C:\Users\PC\.codex\agents\pr-qa-00-project-test.toml`：全局独立测试 Agent 的角色、边界和验收规则；项目内 `.codex/agents/pr-qa-00-project-test.toml` 为维护副本；
- `.codex/skills/scienceresearch-functional-qa/`：科研工作台专用的功能覆盖模型、按钮无响应判定规则和报告格式；
- 用户级 `$playwright` Skill：OpenAI curated 浏览器自动化 Skill，用于真实页面点击、表单填写、截图、trace、网络和控制台检查。

`pr-qa-00-project-test` 是只读验收角色。它可以启动隔离的本地服务、创建临时测试数据和保存测试证据，但不会修改产品代码、正式文档或正常 `data/` 目录，也不会把失败项自动改成通过。

它固定使用 `$scienceresearch-functional-qa` 建立覆盖模型，并在可用时使用 `$playwright` 做真实浏览器交互。它的输入应是已确认的 Must 范围、SRS/SDD、用户手册和待测实现；科研成效卡、论文或仿真图可作为产品需求的背景证据，但不能替代可测试的软件验收条件。

## 2. 启用方式

Agent 和新安装的 Skill 在新的 Codex 会话中加载。关闭并重新打开当前项目会话，工作目录保持：

```text
E:\zl\01-Project\scienceresearch
```

然后使用以下提示：

```text
调用 pr-qa-00-project-test agent，使用 $scienceresearch-functional-qa 对 scienceresearch 执行完整功能测试。逐项测试所有页面、链接、按钮、表单、JavaScript 交互和 API，重点检查点了没反应、返回状态或正文不正确、页面显示与服务端状态不一致、控制台错误、窄屏溢出和键盘不可用。使用临时数据目录，不修改正常 data；把报告、截图和 trace 保存到 output/pr-qa-00-project-test，并给出 PASS/FAIL/BLOCKED 结论和可复现缺陷清单。
```

也可以执行有针对性的测试：

```text
调用 pr-qa-00-project-test agent，只复测周计划、Evidence、完成门、Recommendation 和报告导出，核对每个按钮的可见结果、HTTP 返回和数据库状态。
```

```text
调用 pr-qa-00-project-test agent，检查主工作台所有按钮是否有响应，并在 1440、900、390 三种宽度执行键盘和布局测试。
```

## 3. Agent 的检查方法

Agent 首先从需求文档、设计方案、项目架构、用户手册、`web.py`、`core.py` 和现有测试建立覆盖清单，而不是只根据页面上当前存在的元素判断是否正确。

对每个按钮、链接或表单，Agent 至少检查：

1. 操作前后的 URL 和页面状态；
2. 是否产生预期的可见反馈；
3. 请求方法、路径、HTTP 状态、Content-Type 和正文结构；
4. 浏览器 console、page error 和失败请求；
5. 页面刷新后的持久化状态；
6. API、页面显示和数据库状态是否一致；
7. 缺少前置条件、错误输入、重复提交和过期版本是否被正确拒绝。

如果点击后既没有跳转、可见反馈、请求、状态变化，也没有可访问的解释，会标记为 `NO_RESPONSE`。如果发生了动作，但状态码、正文、重定向、页面结果或持久状态错误，会标记为 `WRONG_RESPONSE` 或 `STATE_MISMATCH`。

## 4. 测试证据和结论

每次运行使用：

```text
output/pr-qa-00-project-test/<run-id>/
```

保存测试报告、覆盖矩阵、截图、trace、响应证据和测试命令输出。最终结论只有三种：

- `PASS`：全部 Must 项有可观察证据，且没有 Critical/High 缺陷；
- `FAIL`：存在功能错误、无响应按钮、错误返回或未满足 Must 的项目；
- `BLOCKED`：经过诊断后，运行环境仍然阻止有意义的测试。

测试报告不会只列失败项，还会列出每个已测试功能的预期、实际结果和证据位置。

## 5. 修复与复测流程

推荐流程为：

```text
pr-qa-00-project-test 独立测试
  → 工程师 Agent 按缺陷 ID 修复
  → pr-qa-00-project-test 只复测受影响功能和相邻回归范围
  → pr-pm-00-project-manager 做需求/设计对齐与交付状态判断
```

测试 Agent 本身不实施修复，避免同一个角色既修改代码又证明自己的修改正确。

## 6. 与科研流程的边界

`pr-qa-00-project-test` 不验证科学结论、实验可重复性或论文 claim。这些由 `sr-experimenter`、`sr-critical-reviewer` 与 `sr-principal-investigator` 按 SR 工作流处理。只有科研项目负责人和人类决策者确认某项科研成果需要转化为科研工作台功能，并经 `pr-pm-00-project-manager` 形成可验收的软件范围后，项目测试才进入该功能的交付链。
