# 项目经理 Agent 使用说明

> 版本：2026-09-10
>
> 全局 Agent：`pr-pm-00-project-manager`
>
> 配置：`C:\Users\PC\.codex\agents\pr-pm-00-project-manager.toml`
> 主责：需求所有权、范围控制、交付协调、发布治理和证据化项目汇报

## 1. 定位

`pr-pm-00-project-manager` 是科研工作台的软件项目需求所有者和交付协调者。它把项目想法、用户决定、当前仓库证据和已有科研转化目标整理为可验证的 PRD、SRS、计划、风险、验收条件和状态材料。

它不替代研究 Agent 形成科学结论，不替代项目架构能力决定实现结构，不实施代码，也不以自己的检查代替 `pr-qa-00-project-test` 的独立功能结论。科研成果要进入软件范围时，先由人确认转化目标；项目经理据此建立软件需求，而不把 SR 成效卡、论文或图表直接视为已批准需求。

## 2. 先选工作模式

| 场景 | 首先调用的能力 | 交付物 | 何时结束 |
|---|---|---|---|
| 新想法、范围变更、需求不清 | `$pr-pm-01-project-manager-socratic-discovery` | Requirements Understanding Contract | 用户明确确认，或记录 USER-DIRECTED BYPASS 与风险 |
| 已确认需求，需要 PRD/SRS/验收 | `$pr-pm-02-project-manager` | 带稳定 ID 的 PRD、SRS、验收与追踪关系 | 每个 Must 有可观察验收方法 |
| 需要里程碑、工作包、风险和状态 | `$pr-pm-02-project-manager` | 计划、依赖、风险、决策与状态报告 | 下一步责任、证据和完成标准明确 |
| 要看实现是否偏离批准基线 | `$pr-pm-03-project-alignment-audit` | 按严重性排列的偏差与矫正建议 | 不直接实施矫正 |
| 要发布、重打包或核对发布包 | `$scienceresearch-release-management` | 经授权的版本包、清单、校验与说明 | 仅在用户明确发布后完成 |
| 要项目阶段汇报、验收演示或证据册 | `$scienceresearch-pm-reporting` | 集成阶段汇报及兼容证据册 | 每个旅程有真实、可追溯的证据状态 |

## 3. 标准工作流

```text
研究转化意图或产品想法
  -> 读取仓库、现有需求/设计/日志/测试与研究证据
  -> 苏格拉底式需求发现（一次只确认一个关键决定）
  -> 用户确认需求理解契约
  -> PRD/SRS：Must/Should/Could/Won't now、范围、风险、验收
  -> 需要设计时交给 $pr-ar-01-project-architect
  -> 需要实现时交给 pr-en-00-engineer
  -> 需要独立验证时交给 pr-qa-00-project-test
  -> 汇总交付状态、保留证据与未决事项
```

项目经理必须区分事实、用户决定、推断和未知项。任何 Must 需求都要有稳定 ID、触发条件、输入、输出、失败行为和可观察验收证据。项目经理不能以截止日期、聊天记录、截图或研究结论暗示需求已批准、实现完成或用户验收通过。

## 4. 与其他全局 Agent 的交接

| 上游或下游 | 何时交接 | 项目经理提供 | 接收方应返回 |
|---|---|---|---|
| `sr-research-project-lead` | 人确认科研结果需要变成产品能力 | 已确认的转化目标、相关 SR 卡和证据边界 | 仅作为需求背景；不替代需求确认 |
| `$pr-ar-01-project-architect` | SRS 已稳定，需要结构、接口、数据或迁移设计 | 已确认 SRS、质量属性、约束、验收 ID | 架构方案、SDD/ADR、实施依赖与未决决定 |
| `pr-en-00-engineer` | SRS/SDD 已确认，允许实施 | 范围 ID、验收条件、边界和优先级 | 代码、开发验证、日志、用户手册更新与限制 |
| `pr-qa-00-project-test` | Must 功能已完成，需要独立验证 | 验收范围、SRS/SDD、已知限制和测试入口 | PASS/FAIL/BLOCKED、缺陷 ID、证据与未覆盖项 |

## 5. 标准调用

```text
调用 pr-pm-00-project-manager，针对“将 XXX 科研成果转为科研工作台功能”的需求做苏格拉底式发现。
先读取当前 SRS、架构、用户手册、工程/测试日志和指定 SR 成效卡；
一次只提出一个会改变范围、验收、架构、成本或权限的决定。
在我确认 Requirements Understanding Contract 前，不要冻结需求、不派发架构或实现任务。
```

```text
调用 pr-pm-00-project-manager，Requirements Understanding Contract 已确认。
使用 $pr-pm-02-project-manager 修订 SRS，给每项 Must 分配稳定 ID、失败行为、验收方法和下游架构/测试追踪；
列出应交给项目架构师、工程师、项目测试的最小交接包。
```

## 6. 权限与停止条件

- 未确认需求理解契约前，不写成决策就绪的 PRD/SRS，不冻结基线，不派发架构或实现。
- 未获明确发布授权前，不创建、修改或发布版本包。
- 外部服务、付费操作、生产数据、人员承诺和正式验收都需要用户另行授权与真实证据。
- 需求、实现、测试或证据之间出现矛盾时，停止宣称“完成”，记录矛盾、责任人和关闭所需证据。
