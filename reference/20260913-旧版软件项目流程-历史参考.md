# 
1.已确认功能回归防错规则

以下规则适用于修复、重构、界面精修、预览布局调整和需求回正；其目标是防止“核心能力还在，但用户在当前主页面已经用不到”的假完成。除非用户明确批准替代或废弃，已经确认、已实现或已经在用户手册/验收证据中展示过的功能都属于兼容性基线，不能因新功能合入而悄然消失。

1） **先做回归影响清单，再改可达入口。** 修改页面组合、路由、渲染器、函数别名、CSS 入口或状态管理前，工程师必须列出该入口原有的用户可见能力、对应需求/设计 ID、领域方法、Web 路由和测试；不得只比较新旧 HTML 结构。特别要检查“核心/数据库方法仍存在，但 Web 页面、按钮、路由或样式未接线”的情况。
2） **每个用户路径只能有一个可达组合根。** 同一主页面不得长期保留多套竞争的 renderer、模板、函数重定义或文件末尾别名覆盖。若因迁移暂时保留旧实现，必须标记为不可达或删除，并新增自动检查，确认实际 HTTP 路由调用的唯一 composition root、状态机、CSS 和脚本来自同一实现单元；禁止用后置赋值悄悄覆盖较完整的实现。
3） **界面重构必须保持全量已确认功能。** 改变布局（例如目录/详情、手风琴、预览侧栏）时，项目经理先判断是否与现有需求或设计冲突；用户作出新的布局决定后，必须同步更新 `idea.md`、需求文档、设计文档和验收条款，再实现。工程师必须将原有功能合并进新的可达页面，至少逐项核对状态颜色/徽标、详情字段、展开收起、筛选、进度、删除确认、预览、失败回退和可访问性；不能以“新布局存在”替代旧功能的兼容性验收。
4） **状态既要派生，也要可见。** 由领域数据派生的颜色、徽标、计数、完成状态和进度，必须同时有唯一的视图规则、CSS/token、文字辅助和真实页面断言。不得只输出 `state-*` class 而遗漏 CSS，不得把颜色作为数据库真源；完成、成效、空态等优先级必须在需求/设计中明示，并验证状态变化和刷新/重启后仍一致。
5） **交互验收必须覆盖“点开—再点收起—切换—恢复”。** 对工作包、成效卡、折叠区、预览和筛选等交互，测试至少验证初始状态、首次点击、重复点击、切换到另一对象、键盘 Enter/Space、无 JavaScript 的 GET/表单降级、刷新/历史恢复和对象所有权隔离。不得以元素存在、字符串匹配、HTTP 200 或单一 Core 单测代替用户可见的完整操作链。
6） **领域能力必须做 Web 端到端接线验证。** 已有 Core/API 方法（例如进度计算、删除 Saga、状态更新、文件预览）只有在当前产品入口能从用户操作到达、能返回可理解结果、能覆盖失败/拒绝路径并在必要时持久化后才可报告为“已实现”。核心单测通过只能证明领域能力，不证明产品功能可用。
7） **高风险操作必须验证完整安全链。** 删除、归档、永久清理、文件移动、权限/状态变更等操作必须从网页入口验证独立确认、分支选择、prepare/commit、版本冲突/失败不误报成功、恢复或 `CLEANUP_PENDING` 提示、审计记录和数据/附件实际结果；禁止用浏览器 `confirm()` 或只测领域 Saga 代替产品流程。
8） **编码问题以原始响应为准。** 发现中文乱码时，测试员必须检查 HTTP `Content-Type`、原始响应字节、严格 UTF-8 解码、`U+FFFD` 替换字符和关键真实 Unicode 文案；不得把 PowerShell/终端代码页显示直接认定为浏览器页面乱码。反之，若原始响应确有编码问题，必须用 HTTP 回归锁定，不能靠全文件盲目转码修复。
9） **验收顺序和结论必须如实闭环。** 每轮修改后先由工程师运行针对性回归与全量门禁，再由项目经理按需求/设计检查实际可达路径，最后由独立测试员以隔离数据复验。任一方发现 High/Critical 缺陷即为 `FAIL`，必须回派工程师并重新验收；不得用旧报告、旧截图、旧测试计数或“此前通过”覆盖当前文件状态。浏览器工具受环境阻断时，应记录降级基线、保留已取得的真实 HTTP/原始响应证据和未覆盖项，不得伪称浏览器已验证。
10） **防回归测试是交付物，不是附属品。** 每个本次发现的回归都要新增或加强最小自动化资格测试，测试名称应表达用户路径和结果；测试应失败于修复前、通过于修复后，并覆盖主页面实际路由。项目经理与测试员验收报告必须分别链接该测试、执行命令、隔离数据/证据和剩余限制。
